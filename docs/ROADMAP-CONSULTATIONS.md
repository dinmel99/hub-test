- Статический GitHub Pages; основные страницы: `index.html` (~563 КБ), `partner.html` (~38 КБ), `partner-admin.html` (~11 КБ).
- В `index.html` сосредоточены интерфейс, стили, бизнес-логика и обращения к Supabase; в репозитории нет отдельных исходных модулей, package.json и автоматизированных тестов.
- На текущем этапе Supabase Auth/DB/Storage управляет регистрацией, доступами и данными. Перед переработкой необходимо зафиксировать текущие RLS, схемы и RPC, которых в репозитории нет.
- `proxy-test/index.html` — отдельная крупная копия. Не удалять без проверки необходимости.
- Не смешивать личные клиентские данные с публичными каталогами и обезличенной телеметрией.

## Безопасная последовательность работ

1. Сохранить неизменяемый `main` и работать через ветки/PR.
2. Добавить проверку синтаксиса JS, ссылок на локальные ресурсы и базовую проверку запуска/авторизации. Затем рефакторинг небольшими партиями с проверкой после каждого шага.
3. Выделить модули по зонам: `auth`, `catalogs`, `partners`, `mortgage`, `clients`, `consultations`, `analytics`. Не менять формат данных и поведение в одной операции.
4. Подготовить миграции Supabase и отдельные роли для консультаций; публичные страницы не должны получать доступ к персональным данным.
5. Создать кабинет `consultations.html` с авторизацией, списком клиентов, консультациями, событиями, задачами, фильтрами и воронкой.
6. Импортировать Google Sheets «Воронка консультаций» (сухой прогон, предпросмотр, контроль дублей и ручная проверка), сохранить оригинал.
7. Привязать существующие каталоги и создание КП к карточке консультации через идентификаторы клиента; не дублировать генератор КП.
8. После проверки первого консультанта добавить назначение исполнителей и разграничение доступа для будущей команды.

## Модель консультаций

- `consultation_clients`: id, workspace_id, owner_id, consultant_id, name, phone, budget, land_status, technology, mortgage_type, down_payment, created_at.
- `consultations`: id, client_id, consultant_id, occurred_at, summary, outcome, created_at.
- `consultation_actions`: id, client_id, consultant_id, due_at, status, title, completed_at, created_at.
- `consultation_events`: id, client_id, actor_id, type, payload, created_at.
- `consultation_pipeline`: stage, status, commission_amount, updated_at (лучше отдельная история изменений этапов).
- Сразу проектировать `workspace_id` и membership, но пока доступ только владельцу. Проверки доступа — **RLS в Postgres**, не CSS/JavaScript.
- Фиксировать события отдельно, не перезаписывать историю строкой «Следующее действие». Просрочка — только для невыполненных задач активных клиентов.

## Нельзя делать до проверки

- Не выкладывать реальные телефоны, ФИО, расшифровки консультаций или экспорт таблицы в публичный репозиторий.
- Не коммитить пароли, JWT, service_role ключи, файлы резервных копий и конфигурацию со служебными секретами.
- Не включать автоматический сбор персональных данных в сервис аналитики.
- Не запускать SQL миграции на рабочей базе, пока не проверены политики доступа, процедура отката и резервная копия.
- Не удалять/перемещать файлы, пока ссылки и GitHub Pages не проверены.
